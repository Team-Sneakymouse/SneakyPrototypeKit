# Item text dialogs in Paper 26.2

Research date: 2026-10-01. The implementation now uses prefilled Name and Lore dialogs.

Replacing the name and lore chat prompts is feasible with the existing Paper 26.2 dependency. Native dialogs arrived in Minecraft 1.21.6 and Paper's API in 1.21.7. Paper supports creating dialogs during gameplay and showing them to a player, without registering a datapack or adding a client mod. [Paper dialog guide](https://docs.papermc.io/paper/dev/dialogs/), [26.2 Dialog API](https://jd.papermc.io/paper/26.2/io/papermc/paper/dialog/Dialog.html)

## Fit for this plugin

`DialogInput.text` accepts an initial string and a maximum length. Name can remain a single-line field with `maxLength(30)`; lore can use `maxLength(100)`. Prefill each field from the prototype's persistent data so players can edit existing values. Input width supports 1–1024. Lore can optionally enable multiline with a height of 1–512 and an optional maximum line count. [26.2 text input](https://jd.papermc.io/paper/26.2/io/papermc/paper/registry/data/dialog/input/TextDialogInput.html), [26.2 multiline options](https://jd.papermc.io/paper/26.2/io/papermc/paper/registry/data/dialog/input/TextDialogInput.MultilineOptions.html)

Save and Cancel can be the two buttons of a confirmation dialog. Paper supports a local `DialogAction.customClick` callback, and `DialogResponseView.getText(key)` retrieves the submitted string. This avoids routing text through commands or intercepting chat. Callbacks default to one use and a 12-hour lifetime, so invalid submissions need a fresh dialog/callback to allow retry. [Paper callbacks](https://docs.papermc.io/paper/dev/dialogs/#using-callbacks), [26.2 response view](https://jd.papermc.io/paper/26.2/io/papermc/paper/dialog/DialogResponseView.html)

The former chat input used raw Kotlin `String.length` limits and required admin permission for formatting. The dialog handler retains those rules, updates the prototype's persistent data, and reopens the creation menu. Inventory button handling and response processing schedule transitions for the next tick. [Dialog handler](../../src/main/kotlin/net/sneakyprototypekit/creation/ui/ItemTextDialog.kt), [Creation flow](../../src/main/kotlin/net/sneakyprototypekit/creation/ui/MainCreationListener.kt)

## Drawbacks and design decisions

- Text fields edit plain strings. They do not provide a rich text editor for the plugin's `&` codes or MiniMessage tags. Keep the existing format permission guard and conversion. A formatted preview can be a dialog body, but the available API sends values on an action, so a server-rendered preview requires a Preview button and another response/dialog. [26.2 text input](https://jd.papermc.io/paper/26.2/io/papermc/paper/registry/data/dialog/input/TextDialogInput.html), [26.2 action API](https://jd.papermc.io/paper/26.2/io/papermc/paper/registry/data/dialog/action/DialogAction.html), [Text conversion](../../src/main/kotlin/net/sneakyprototypekit/util/TextUtility.kt)
- Player lore now uses `TextUtility.renderPlayerLore`, which preserves explicit newlines, blank lines, and formatting across lines. Each explicit line wraps at 30 visible Unicode characters, preferring whitespace boundaries and splitting long words when needed. Ability descriptions still use `wrapLore`. The input has a width of 188 GUI pixels, approximately 30 ordinary glyphs plus padding. It cannot guarantee a fixed character count because glyph widths vary. Existing player lore without newlines also wraps automatically. [Lore rendering](../../src/main/kotlin/net/sneakyprototypekit/util/TextUtility.kt), [Dialog handler](../../src/main/kotlin/net/sneakyprototypekit/creation/ui/ItemTextDialog.kt)
- Client limits improve editing, but do not replace server validation. Paper explicitly gives no guarantee that a response came from a real dialog form. Validate player/session, missing values, length, formatting permission, and stale submissions before saving. `getText` can return null. [26.2 response view contract](https://jd.papermc.io/paper/26.2/io/papermc/paper/dialog/DialogResponseView.html)
- Dialogs are modal, have constrained layouts, and replace an already visible dialog. Another plugin opening a dialog may interrupt editing. Closing normally restores the previous non-dialog screen. Escape runs the dialog's exit action; a confirmation dialog uses its negative action, making Cancel a suitable return path. [Mojang dialog specification](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-6#dialogs)
- `closeDialog()` retains an underlying inventory, while `closeInventory()` closes both screens. Decide whether to keep the creation inventory underneath or rebuild it after Save/Cancel, then test that flow in game. [Paper closing behavior](https://docs.papermc.io/paper/dev/dialogs/#closing-dialogs)
- Minecraft introduced dialogs as experimental custom content with a warning button beside their title. That is a client UI caveat, separate from API annotations. The examined Paper 26.2 `Dialog`, `DialogAction`, and `DialogResponseView` declarations have no `@Experimental` annotation. No later primary-source statement removing the Minecraft warning was found; verify its appearance with a 26.2 client. [Mojang introduction](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-6#dialogs), [26.2 Dialog declaration](https://jd.papermc.io/paper/26.2/io/papermc/paper/dialog/Dialog.html)
- Native dialogs require a dialog-capable Java client. A vanilla 26.2 client meets that requirement. Older clients admitted through protocol translation and Bedrock clients through a bridge need separate compatibility testing or a fallback. This is a compatibility inference from the feature's introduction in Java 1.21.6. [Paper introduction](https://docs.papermc.io/paper/dev/dialogs/)

Use custom-click responses for text. Mojang specifies that text sent as a tag preserves its contents, whereas command-template substitution escapes characters for an SNBT literal. A callback avoids adding command quoting rules to item text. [Mojang text input specification](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-6#input-control-types), [26.2 custom-click action](https://jd.papermc.io/paper/26.2/io/papermc/paper/registry/data/dialog/action/DialogAction.html)

## Implemented behavior

Each existing Name/Lore button opens a prefilled confirmation dialog with Save and Cancel. The 30/100 raw character limits and formatting permissions remain. Lore accepts multiline input; player line breaks and blank lines are retained, with automatic wrapping inside each long line. Invalid input reopens with the submitted draft and an error message. Empty input clears the saved field. Callbacks check the player, originating editor inventory, current dialog token, and kit presence before accepting input. Save and Cancel rebuild the item editor on the main thread, and Escape uses Cancel.

`gradlew.bat build` passed, including seven tests for explicit and automatic breaks, blank lines, word boundaries, long words with supplementary Unicode characters, formatting across breaks, and ability wrapping. No 26.2 client was run. Before shipping, check Save, Cancel/Escape, invalid-format retry, editing existing text, and inventory restoration in game, and adjust the approximate input width if needed.
